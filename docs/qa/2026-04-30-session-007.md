# 2026-04-30 Session 007

## Topic

Neon database visibility, local run commands, and auth write-path verification.

## Questions

1. Why did Neon show no user rows when logins appeared to work?
2. What is the correct local command flow for backend, frontend, migrations, and checks?
3. What should be verified before Phase 3 starts?

## Answers

1. The first successful-looking auth flow was not proof of a current Neon write. A stale Python API process was still holding port `8000`, browser auth state can remain in `localStorage`, and backend tests use temporary SQLite databases instead of Neon.
2. The backend should be run from `apps/api` with migrations applied first, then started through direct `uvicorn`. The frontend should be run separately from `apps/web` on port `3000`.
3. A fresh signup should create rows in `users`, `profiles`, and `refresh_tokens` in Neon.

## What Was Happening

- Neon was correctly connected in the current backend environment, but the visible browser session could still look authenticated from stored client tokens.
- A previous Python process on port `8000` could serve old code or use an old environment, so responses from that process did not prove the current backend was writing to the configured Neon database.
- Once the backend was restarted cleanly against Neon, signup exposed a PostgreSQL foreign-key ordering issue: the refresh token could be flushed before the user row.
- SQLite tests did not catch that behavior earlier because the test database was temporary and did not enforce foreign keys until the fixture was tightened.

## Decisions Taken

- Keep local frontend development pinned to `http://localhost:3000`.
- Keep local backend development on `http://127.0.0.1:8000`.
- Prefer this backend command on Windows:

```bash
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

- Do not rely on the FastAPI CLI as the primary Windows command because the CLI startup banner can fail in terminals that cannot encode its Unicode output.
- Treat Neon verification as a real API smoke test, not as a pytest result.

## Local Setup Flow

Backend terminal:

```bash
cd apps/api
uv sync
copy .env.example .env
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Frontend terminal:

```bash
cd apps/web
npm install
npm run dev
```

Open the product:

```text
http://localhost:3000
```

Backend health check:

```text
GET http://127.0.0.1:8000/health
```

Verification terminal:

```bash
cd apps/api
uv run pytest
uv run ruff check .
uv run ruff format --check .
cd ../web
npm run lint
npm run typecheck
npm run test
npm run build
```

## Neon Verification Checklist

- Restart the API after editing `.env`, migrations, or auth code.
- Clear browser site data or sign out before testing a fresh signup.
- Create a new account through the running app or `POST /auth/signup`.
- Refresh Neon tables and confirm new rows appear in `users`, `profiles`, and `refresh_tokens`.
- If the browser looks logged in but Neon has no rows, assume stored client tokens or a stale API process before assuming the database failed.
