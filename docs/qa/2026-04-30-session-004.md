# 2026-04-30 Session 004

## Topic

Refining the frontend from implementation-facing scaffolding into a SaaS-style user journey with real landing, signup, login, and workspace entry flow.

## Questions

1. Should the frontend continue showing technical and implementation-facing content?
2. Should the client be refined around a SaaS-style user journey instead?
3. What screens should be prioritized in this pass?
4. Should signup and login be wired to the backend auth routes now?
5. From a product perspective, what should happen right after auth?

## Answers

1. No. The client should not explain backend setup, implementation phases, or internal engineering concerns to end users.
2. Yes. The frontend should be shaped like a real SaaS product, with the flow designed from the user and product-manager perspective.
3. Prioritize the landing page, signup page, login page, and the first workspace entry screen.
4. Yes. Signup and login should be functional against the existing backend auth APIs.
5. Users should land in a simple workspace entry screen that makes the next high-value action obvious, instead of dropping them into a vague or technical shell.

## Decisions Taken

- Remove implementation-facing messaging from the landing flow.
- Position the home page like a real SaaS landing page with clear product value and auth entry points.
- Add dedicated `/signup` and `/login` flows wired to the Phase 2 backend auth APIs.
- Add a `/workspace` entry route that acts as the post-auth handoff into onboarding and resume creation.
- Keep the product messaging focused on upload/template choice, progressive onboarding, version-safe editing, and job targeting.

- Functional browser-side auth now depends on local CORS support from the backend.
- The next frontend milestone is no longer “build auth screens”; it is “build onboarding and real workspace actions.”
